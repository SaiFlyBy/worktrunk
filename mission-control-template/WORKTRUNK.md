# Worktrunk and Mission Control

This fork includes Mission Control v16 and a bridge that creates a Worktrunk
worktree for one compiled mutation cell. Python 3 and Worktrunk 0.81.0 or
newer must be available. Initialize and compile a mission with the normal
[Mission Control operator commands](README.md) first. Keep a matching
source checkout available, or extract the full platform release archive. The
archive includes `flyby-integration/mission-control-template` and the associated
attribution. The standalone shell and PowerShell installers install Worktrunk
binaries only; they do not install Mission Control. On Windows, pass the full
path to the archive's `wt.exe` with `--wt` if Windows Terminal owns `wt`.

Once the cell is compiled, create its workspace and assign separate worker and
verifier identities:

```sh
python path/to/mission/runtime/tools/wt_mission.py prepare \
  --root path/to/mission --repo path/to/target \
  --cell M000 --workspace-id ws-M000 --branch mission/m000 \
  --worker worker-M000 --verifier verifier-M000
```

`--repo` is the existing target worktree root. `--path` may specify a
new worktree directory; otherwise Worktrunk chooses it. The adapter checks
the compiled repository against `origin`, creates the branch from the exact
compiled base, suppresses Worktrunk and Git checkout hooks for that creation,
and asks Mission Control to register the clean workspace before dispatch.
Git's full reported status must be clean; configure the target repository's
normal ignore rules for generated bytecode rather than hiding reported files.
For a nonstandard origin, an operator who has verified it may supply its exact
URL with `--expected-origin`. Registration or dispatch failure leaves the
worktree in place for inspection. The bridge does not start or replay hooks:
run approved setup only after dispatch has granted the cell's resource claims.

Omit both `--worker` and `--verifier` to register without dispatch.
Mission Control's ordinary `dispatch` command can start it later. A conflict
in the class or resource claims remains a Mission Control dispatch error.

Inspect the independent adjudication, requirement links, candidate head and
evidence references for a scope:

```sh
python path/to/mission/runtime/tools/wt_mission.py report \
  --root path/to/mission --cell M000
```

The report is a bounded, read-only projection, not a new decision or evidence
that an unrecorded check ran. Settlement still needs the result, context
receipt, attempt number and separate verifier adjudication:

```sh
python path/to/mission/runtime/tools/wt_mission.py settle \
  --root path/to/mission --cell M000 --attempt 1 \
  --result result.json --context-receipt receipt.json --adjudication adjudication.json
```

An explicitly requested publication uses the accepted workspace head and opens
one draft PR. It checks every effective push destination against the compiled
GitHub repository, the live remote base, the branch and the accepted evidence.
The push binds one of those verified destinations to that invocation, including
when Git URL rewrites are configured. It checks that Git supports clearing a
push URL list for one command and stops before upload if that capability is
missing. A new remote branch is created with an atomic absence lease; an
existing branch is never overwritten. It never
squashes, rebases, merges or deletes a worktree:

```sh
python path/to/mission/runtime/tools/wt_mission.py publish \
  --root path/to/mission --cell M000 --base main \
  --title "Complete one coherent scope" --body "Evidence and limitations"
```

Publication checks that the current remote base is an ancestor of the exact
independently accepted candidate. If main advanced but was included before
verification, the scope can proceed without a separate aggregate branch. If
the current base is absent or cannot be checked locally, publication stops and
the branch is preserved. A failed or uncertain push or PR creation must be
reconciled before retrying.

Before reporting publication success, the bridge reads the resulting PR and
checks its repository, branch names, head and base commits, and open state. A
new PR must still be a draft. It then reads the remote refs again. The same
checks apply when reconciling an existing PR, without changing its review state.
A failed read or a changed candidate/base leaves the branch and any PR intact
and requires reconciliation before retrying. This is an observed receipt, not
an atomic transaction across Git and GitHub: another actor can still change a
ref afterward. Review and acceptance must remain bound to the candidate commit.

### Concurrent scopes

Linked worktrees already reuse Git's object store; they do not need separate
clones or object transfers to integrate local branches. Working trees and indexes
are separate, but ordinary branch refs are shared. Worktrunk advances branches
with Git's expected-old-commit comparison, and the bridge creates a published
branch only if that remote ref is absent. Independent branch publications do
not take a repository-wide bridge lock. Competing publications to the same
absent ref cannot overwrite one another; reconcile the winning ref before retrying.
Mission Control still coordinates its shared mission state and resource claims.

These boundaries apply the per-ref coordination and immutable-object lessons
from [Scaling Git at OpenAI](https://openai.com/index/scaling-git-at-openai/).
They do not add a storage backend, custom Git flags, automatic fetches, or pack
cleanup. Git continues to own object validation, ref transactions, and transport.
The bridge's tests synchronize real local pushes to exercise independent refs
and competing creators, and inject changes around forge reads to check that
publication rejects mismatches observed during final verification.
If main advances after a scope was accepted, first fetch the actual current
base using the project's normal Git workflow. Pass its exact locally available
commit to `handoff` while the mission is still in its mutation phase:

```sh
python path/to/mission/runtime/tools/wt_mission.py handoff \
  --root path/to/mission --cell M000 --successor M002 \
  --frontier F200 --base-sha ACTUAL_CURRENT_MAIN_COMMIT
```

The bridge checks the original accepted worktree, binds its result, context
receipt and adjudication hashes, and asks Mission Control to compile a new
successor cell with the same requirement, ownership and resource claims. It
records the changed base paths as context, not as a verdict about which tests
remain valid. The original accepted cell and worktree are left intact.

Use `prepare` to register and dispatch the successor at the mission's exact
compiled baseline. After dispatch, the worker can incorporate the accepted
source commit and the observed main commit into that successor worktree using
ordinary Git merges; resolve any conflicts there. Reassess prior evidence
against the resulting candidate, the changed inputs, dependencies, test
selection and toolchain. Reuse evidence only where those premises still hold;
rerun or explicitly account for affected or uncertain checks. An independent
verifier must adjudicate the successor before `publish` can open its draft PR.
The live remote base is checked again at publication. No evidence is marked
valid and no merge, rebase, force push or cleanup happens automatically.

The current v16 lifecycle allows this successor before integration begins.
After the mission has moved to integration or later, a new mission is needed;
carry forward the original evidence references and reassess their applicability
rather than treating previous checks as automatically valid.

For final workspace accounting, prepare the reconciliation required by v16,
then load it and optionally close:

```sh
python path/to/mission/runtime/tools/wt_mission.py reconcile \
  --root path/to/mission --file workspace-reconciliation.json --close
```

The bridge does not make a local aggregate branch. Mission Control's existing
integration, qualification and closure evidence still applies. Worktrees and
both accepted heads remain in the workspace reconciliation until their
retention or cleanup has been independently accounted for.

## Qualification dependencies

The path-scoped `mission-control-bridge` workflow builds the fork's own `wt`
binary and runs the bridge, v16 lifecycle and reference-fixture checks on
Linux and Windows. This focused CI job does not claim the original template's
full four-layer qualification. The original source-workflow custody and MCV6
legacy-fixture proofs still belong to the retained full proof inventory; they
require the private source repository and cannot run in public hosted CI
without separately arranged read-only access.

For a local full proof, provide a clean checkout of
`SaiFlyBy/flybyrefactor` at `29efd0ffcac21717fd789da2c7020a7e02501e00`
with its `.github` workflows and `archive/mission-control-v6` materialized.
The legacy fixture also references historical Git objects; ensure the original
repository can retrieve those objects. Set `MC_SOURCE_PROOF_REPO` to that
checkout's absolute root and invoke the existing `tools/run_template_suite.py`
with `--environment-mission-root` pointing to its real
`archive/mission-control-v6`. The source-only tests verify the checkout's
origin, exact commit and cleanliness before using it. The archive remains in
the source checkout and is not published in this fork. The proof runner still
requires all four layers and does not turn missing fixture evidence into a
pass.

The dedicated `cell-candidate` qualification route consumes a private task-owned
source copy under `$RUNNER_TEMP/../worktrunk-cell-fixtures/<source-commit>/<candidate>/source`,
outside the runner's per-job temporary-directory cleanup.
Preparation verifies the original repository, commit/tree and sealed byte hashes;
the job independently checks them again before the complete runner. Credentials
are not copied into this fixture or granted to the job. Its raw proof logs remain
outside the public artifact root; the artifact retains candidate/fixture identity,
layer/command outcomes, timing and log hashes. Required failures still fail the job.
The focused public-source fallback runs only if the complete proof fails and the
run has not been cancelled. Long verification steps honor cancellation. The
changed-base golden mode runs separately; an already-passing ordinary golden run
inside the complete proof is reused. Retain private evidence locally before
removing only task-owned runner inputs.


## Enforceable target-cell coordination

Initialize a **new** mission with `mc init --mission MISSION.json
--cell-coordination` to seal `cell-coordination/v1` and execution-state v19.
Existing frozen missions and their locks are unchanged. A v16 frozen runtime
does not acquire this protection; bootstrap repair never upgrades its assets.

Declared target paths now participate in admission alongside explicit resource
claims, conflict classes, and ACCEPTED dependencies. A trailing slash declares
a directory; an existing directory is also a directory; a nonexistent path
without a slash is an exact file. `src/a` and `src/ab` are distinct. Exact files do not own descendants, but a file/descendant pair conflicts because Git cannot contain both in one tree. Separators
are normalized, links must resolve inside the registered workspace, and links
that alias an owned path conflict. Absolute paths, traversal, Git metadata,
Windows device/alternate-stream aliases, and glob syntax are rejected. Windows
matching is conservatively case-insensitive; elsewhere the Git repository's
`core.ignorecase` contract applies. Do not change filesystem case semantics
under an active authority. Mixed case semantics inside one worktree are outside
this capability's supported filesystem contract.

`dispatch` records an idempotent request and returns `QUEUED` or `ADMITTED` in
`phase`. Requests receive a durable increasing order; conflicting **eligible**
requests use FIFO, with cell identity as the deterministic tie-break. Blocked
dependencies do not reserve paths. Independent eligible cells use separate
worktrees concurrently. `coordination status` explains blockers; `coordination
recover` reassesses eligibility and admits saved requests without launching a
provider. Repeating a request after a lost reply retains its token and generation.
An authority change requires explicit `coordination reassess`, which gives the
reassessed request a new order and generation. It cannot broaden an active scope.

The control directory is the trusted authority. Capable missions register that
authority in the target Git common directory before admission. A different
authority cannot silently govern those same worktrees. After every queued or
active claim has been safely released, `coordination relinquish` can explicitly
clear this registration. Separate clones coordinated by the same mission use
the same target repository identity, but registrations in different clones do
not constitute a universal repository lock. All participating writers must use
the same Mission Control authority and protocol. Unmanaged processes can still
edit files. Architectural coupling across disjoint files needs explicit shared
resources or dependencies; path ownership cannot infer it.

Admission permits the launch protocol, not an unrecorded writer. Before starting
an external worker, record `coordination launching --cell CELL --generation N
--token TOKEN --executor-identity PROVIDER_SESSION_OR_RUN`. Only its first
transition returns `launch_authorized: true`. A replay is observation, never
permission to launch again. The executor identity is a durable run/session
identity, not a reusable PID. A lost launch reply stays uncertain. `running`,
`unknown`, and `stop` record observations or a stop request; they do not claim
the provider was launched, cancelled, or terminated by Mission Control.

Settlement of a coordinated target requires `--generation N --token TOKEN`,
including through `wt_mission settle --reconcile`. Mission Control independently
reads committed, staged, unstaged and all untracked Git paths, including ignored
untracked paths. Both sides of moves are checked with rename detection disabled.
It binds the scope proof to the exact candidate commit/tree, registered base,
workspace, scope and custody. Acceptance requires a clean candidate. Out-of-scope
changes are rejected with path-specific evidence under `scope-denials`; the
workspace and claims remain recoverable. The existing changed-base handoff records an exact accepted-main observation,
checks the safely released source and binds its evidence into the immutable
successor contract. Its scope proof uses that observed base, while retaining
the original registered base and requiring both source and observed heads as
ancestors. Inherited accepted-main changes are excluded from the cell diff;
new out-of-scope changes are still rejected.

Receiving either a successful or failed result does **not** release ownership.
This capability has no qualified provider-tree termination API and reports
`termination_supported: false`. Heartbeat loss, timeout, cancellation and parent
exit leave a launched attempt held. An independent trusted operator must first
stop/fence the exact executor and every possible descendant using a qualified
facility outside this runtime. Record that observation with `coordination
confirm-stop --observation FILE`; the versioned observation binds the current
generation/token, executor, independent verifier and hashed evidence. This is an
explicit operator safety premise, not automatic OS-level proof. If that premise
cannot be established, retain UNKNOWN custody and do not release or retry.
`coordination release` then releases the confirmed claim; repeat confirmation,
release and recovery are idempotent. An unlaunched queued/admitted request can
be released without pretending that any provider executed. Retry cannot reuse
an unreleased attempt, and stale tokens cannot settle or control a newer one.

The bridge rechecks accepted Git scope and writer termination before public
push/PR creation, including the candidate diff against live publication base.
It preserves immutable-commit pushes, destination checks, exact-base ancestry,
create-only refs and ambiguous-outcome reconciliation. These gates prevent
unauthorized managed promotion; they do not sandbox arbitrary external writers.
Transactions use short mission-local OS locks and fsynced atomic state writes;
they never hold a development-wide lock for a worker's lifetime. Filesystem
power-loss guarantees still depend on the platform. Immutable evidence precedes
state transitions so interrupted settlements can reconcile their exact inputs.


After a safely released failed attempt, retry still requires a clean registered
base. Preserve a failed candidate on its own ref before preparing that base, or
compile an explicit successor. Recovery never resets or cleans a worker's
checkout. Historical scope and fence evidence stays hash-checked across retries;
changing underlying operator evidence blocks further authority transitions.
